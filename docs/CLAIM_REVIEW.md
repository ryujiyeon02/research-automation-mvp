# 인과 주장 보존과 의미 검토

2026-11-05에 추가하고 실제 오류 사례로 보완한 검토 단계입니다. 11월 4일 실행에는 적용되지 않았습니다.

**실험 단계입니다.** 인공 사례의 개선과 달리 실제 AMD 문서에서는 정상 주장을 과하게 제외하는 문제가 남아 있습니다. [검증 결과](../reports/2026-11-05_semantic_review_upgrade.md)를 참고하세요.

기존 코드는 모델 응답을 파싱하고 근거 문구가 실제 입력에 있는 주장만 반환했습니다.
그 전 응답과 제외한 주장을 저장하지 않은 것은 실행 기록 설계의 누락입니다.
토큰 절약을 위해 생략해야 하는 작업이 아니었습니다. 이미 보존하지 않은 과거 응답은 복원할 수 없습니다.

## 현재 실행 순서

```text
원문 DB → 관련 문단 선택 → Ollama 추출 → 원본 HTTP 응답 저장
  → JSON/Pydantic 검사 → 근거 문구 일치 검사
  → 문장 번호 부여 → 명확한 구문은 코드 규칙으로 대조
  → 나머지는 주장별 Ollama 원문 속성 읽기 → 역할·상태·범위·전망 여부를 코드로 비교
  → 전달 경로 별도 검토 → 원문 문장 번호·결정 기록
  → supported / rejected / held 결정 → 후보 파일 보존 (기본 DB 반영 없음)
```

CLI의 `extract-claims`와 `scripts/research_pilot.py --stage extract`가 이 경로를 사용합니다.
저수준 `OllamaClient.extract_claims()`는 근거 일치 검사까지 수행합니다.
새 호출부에서는 `extract_reviewed_claims()`를 사용해야 의미 검토를 거칩니다.

## 어떤 오류를 검사하는가

| 항목 | 질문 |
| --- | --- |
| cause_effect | 원인과 결과가 뒤집혔거나 상관관계를 인과로 바꾸었는가? |
| direction | 결과의 증가·감소 방향을 잘못 읽었는가? |
| scope | 정부 소비를 전체 소비로 바꾸는 등 대상이 달라졌는가? |
| qualifiers | 판매 감소를 단순 판매로 바꾸거나 조건·비교 기준·시차를 빠뜨렸는가? |
| modality | 전망·가능성을 이미 발생한 사실로 바꾸었는가? |
| channel | 원문에 없는 전달 경로를 외부 지식으로 보충했는가? |

각 항목은 supported, contradicted, uncertain 중 하나입니다. confidence 점수만으로 채택하지 않습니다.
모델에 전체적인 맞다/틀리다 판정을 맡기지 않고, 원문의 속성을 읽은 결과를 코드가 후보와 비교합니다.

- 인과 역할: 모델이 원문의 원인과 결과가 각각 어느 후보 변수에 해당하는지와 명시적 연결 여부를 읽습니다. 코드가 역할 뒤집기를 판정합니다.
- 변화 방향: 모델에는 후보의 방향 값을 숨깁니다. 원문 결과의 방향을 읽은 뒤 코드가 후보 값과 비교합니다.
- 원인 상태: 후보의 증가·감소·개선 등 표현은 변수 이름 자체에서 읽습니다. 다른 필드에 있는 설명으로 빠진 상태를 보충하지 않습니다.
- 범위: 원문에서 읽은 범위 표현을 후보 결과 변수의 단어와 대조합니다. `government consumption expenditures` 사이에 `nondefense`가 들어가도 단어를 보존하면 일치합니다. `government`와 `nongovernment`는 다릅니다.
- 확실성: 모델에는 후보의 modality를 숨깁니다. 원문의 전망·가능성·조건부 여부와 후보 값을 코드가 비교합니다.
- 조건: 모델의 맞다/틀리다 응답을 사용하지 않습니다. 인식한 비교 기간·명시적 조건·수치와 시차 표현을 코드로 확인하고, 해석할 수 없는 조건은 보류합니다.
- 전달 경로: 위 검사를 통과한 주장에 대해서만 별도로 검사합니다. 새 중간 변수나 경로를 원문 밖에서 만들지 않았는지 확인합니다.

- 모델이 근거를 다시 쓰지 않고 원문 문장 번호를 선택합니다. 코드는 실제 문장과 시작·끝 위치를 연결합니다. 없는 번호와 중복 번호는 허용하지 않습니다.
- 하나라도 contradicted이면 `rejected`, uncertain이면 `held`입니다.
- 모든 항목이 supported여야 통과 후보입니다. 통과 후보의 지지 문장은 후보 근거와 연결되어야 합니다.
- JSON 오류, 누락·중복·범위 밖 주장 ID, 연결·응답 오류는 한 번만 재시도합니다.
- 두 번 모두 실패하면 해당 주장 또는 검토 단계만 `held`로 남깁니다. 기각된 주장은 통과할 때까지 반복 질문하지 않습니다.
- 한 요청에는 주장 하나만 넣으며 요청 안의 ID는 항상 0입니다. 결과를 원래 후보 번호로 되돌리는 일은 코드가 처리합니다.
- 검토 입력이 보수적으로 정한 문맥 예산(프롬프트·스키마 포함 UTF-8 12,000바이트)을 넘으면 요청하지 않고 보류합니다. 긴 문서 자동 분할은 아직 없습니다.
- 기본 동작은 후보 파일 보존이며 DB의 `causal_claims`에 추가하지 않습니다. 실제 소규모 실행에서 기존 제외 주장을 통과시킨 결과를 보고 자동 반영을 기본 해제했습니다.
- `--store-model-supported`를 명시한 경우에만 supported 후보를 DB에 넣습니다. 그 경우에도 상태는 미검증 `reported_claim`입니다. 모델 통과를 인간 검수나 인과 검증으로 승격하지 않습니다.

## 보존하는 기록

`data/llm_runs/` 아래에 고유 ID로 생성합니다. `.gitignore`의 `data/` 규칙이 적용됩니다.
원문에 공개되지 않은 정보가 포함될 수 있으므로 기록 전체를 GitHub에 올리지 않습니다.

| 파일 | 내용 |
| --- | --- |
| `extraction-*.json` | 실제 입력·프롬프트·스키마, HTTP 응답 원문, 파싱 전후 상태, 근거 검사 전 주장, 제외 이유 |
| `review-*.json` | 별도 검토 요청과 응답 원문, JSON 검증 성공·오류 |
| `pipeline-*.json` | 후보 전체, 문서 ID·URL·내용 해시, 위 파일 연결, 주장별 채택·제외·보류 이유 |

원본 응답은 파싱보다 먼저 저장합니다. 잘못된 JSON도 보존합니다.
HTTP 응답 자체가 오지 않은 연결 오류·시간 초과에는 요청과 오류 종류만 남습니다.
서버가 JSON Schema를 지원하지 않아 재요청한 경우 첫 501 응답도 저장합니다.
환경변수 전체, 요청 헤더, 증권사 키·계좌는 이 기록에 넣지 않습니다.

## 비용과 한계

추출은 문서당 1회입니다. 검토는 주장당 원문 속성 읽기 최대 1회와 전달 경로 최대 1회이며, 코드 규칙으로 확인하면 해당 호출을 생략합니다.
형식·연결 오류는 단계별 1회만 재시도합니다. 규칙만 사용한 경우 검토 모델 토큰은 0으로 기록합니다.
모델 서버의 스키마 미지원 501에 대한 형식 전환 요청은 별도이며 생성 토큰이 없는 실패일 수 있습니다.
응답 저장 자체는 LLM을 다시 호출하지 않습니다. Codex는 이 실행 경로에 없습니다.

현재 추출과 검토는 같은 로컬 `qwen3.5:9b`를 사용합니다. 호출을 분리해도 모델 오류가 독립적이지 않습니다.
검토자가 똑같이 오독하면 잘못된 주장이 통과할 수 있고, 정상 주장도 보류·제외할 수 있습니다.
원문의 주장 자체가 사실인지는 이 단계가 검증하지 않습니다. 원문에 있는 주장과 경제적 인과의 진실은 다릅니다.
검토 사유도 모델 생성물이므로 정확한 해설로 그대로 인용해서는 안 됩니다.

코드 규칙은 영어의 명시적 직접 인과 구문, 일부 조건문, `driven by` 구문과 한국어의 제한된 직접 인과 구문을 다룹니다.
규칙은 지원하는 수치·부호·비율·일부 통화기호와 부정·비교 조건을 검사합니다. 모든 단위·동의어를 해석하는 것은 아닙니다.
한국어 부문의 주제를 뒤 절의 지표로 이어받는 경우에도 같은 부문과 원인·결과만 연결합니다.
규칙이 이해하지 못하는 문장은 모델 검토로 넘어갑니다. 범용 문법 분석기나 인과관계 증명기는 아닙니다.
영어·한국어의 제한된 상태 어휘를 사용하므로 미등록 표현, 번역된 변수명, 새로운 범위 별칭은 추가 보정이나 검토가 필요할 수 있습니다.
추출 프롬프트 v2는 변수 이름을 원문 언어로 유지하고, 필요한 상태·범위·비교 기준을 변수에 보존하도록 지시합니다.
`record sales` 같은 수준 표현을 판매 증가로 바꾸어 추론하지 않습니다. 감소한 사상 최대 판매에서 감소를 빼는 것도 허용하지 않습니다.

## 이 컴퓨터의 실행 환경

Homebrew 0.40.14의 JSON 문법 강제 라이브러리 누락을 확인하여 같은 버전의 공식 macOS 배포본을 별도 폴더에서 사용합니다.
원본 설치를 덮어쓰지 않으며, 기존 `~/.ollama/models`의 모델을 재사용합니다. 새 모델은 다운로드하지 않았습니다.
공식 실행 환경은 약 609MB이며 Git에서 제외한 `data/ollama_runtime/`에 있습니다. 설치 도구가 고정된 SHA-256을 검사합니다.

```bash
uv run python scripts/local_ollama.py install
uv run python scripts/local_ollama.py serve
```

프로젝트의 `.env`는 `OLLAMA_BASE_URL=http://127.0.0.1:11435`를 사용합니다. 다른 키는 변경하지 않았습니다.
자동 시작 설정은 만들지 않았습니다. 위 serve 명령은 필요할 때 실행하며, 이미 같은 포트에 서버가 있으면 다시 시작하지 않습니다.
추출과 검토는 모두 8,192 문맥 크기를 사용하며, 서버는 동시 처리 1개·적재 모델 1개로 제한합니다.
Qwen3.5 검토에는 온도 0.6·top_p 0.95·top_k 20·presence_penalty 0·seed 42를 전달합니다.
같은 이름과 enum이 반복되는 구조화 출력에서 반복을 벌점으로 처리하지 않도록 했습니다. seed를 설정해도 완전한 결정성을 보장하지는 않습니다.
검토 출력 한도는 요청당 700토큰입니다. 길거나 불명확한 결과를 무제한 생성·반복하지 않습니다.

실행 평가에는 기존 오해석과 정상 대조 주장, 원인·결과 뒤집기 예시를 함께 넣었습니다.
기대 판정은 Codex가 작성했으며 독립 전문가의 정답이나 정확도 벤치마크가 아닙니다.
실행 방법:

```bash
PYTHONPATH=. uv run python scripts/evaluate_claim_review.py
```

결과는 고유 실행 폴더 `data/review_evaluations/<run_id>/`에 저장합니다.
개별 실행 결과와 발견한 한계는 공개 실행 보고서에 따로 기록합니다.

저장된 모델 응답으로 코드 변경의 결과를 재현할 때는 다음 도구를 사용합니다. 요청 내용이 저장된 요청과 정확히 맞아야 하며, 새 모델 호출로 넘어가는 대체 경로는 없습니다.

```bash
PYTHONPATH=. uv run python scripts/replay_claim_review.py data/review_evaluations/<run_id>/receipt.json
```

재현 결과는 실제 새 모델 실행과 구분하여 `data/review_replays/`에 저장합니다.
